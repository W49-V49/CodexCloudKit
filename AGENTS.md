# CodexCloudKit project workflow

At each task start, read this file, the business goal, its acceptance commands and the active checkpoint. Estimate task duration and persist the estimate and next action. Work in the selected task repository; shared tools and persistent state stay in configured external directories.

Attach the shared skills without replacing project-specific rules. Retrieve concise verified memory progressively from the current goal, dependencies, previous failures and evidence gaps. Expand recall when needed; there is no fixed token budget or retrieval count. Reuse unchanged content hashes, version fingerprints and same-session bodies. Record verified conclusions with a category, source, applicability, status and test evidence. Store logs separately from curated facts.

Use real agents and subagents for useful independent work. Assign one writer per shared file and preserve concrete handoffs. Agent templates are configuration; count actual spawned workers separately.

For tasks estimated above one hour, establish the configured event continuation and hourly inspection before extended work. Persist checkpoints before dispatch. Recover from the latest durable state and revalidate changed inputs. Archive repeated errors; after two same-class failures or three attempts without progress, trip that route and try an applicable independent backend. Avoid indefinitely replaying the same command.

A model response or successful worker exit is not business acceptance. Run the configured build, behavior and acceptance commands independently. Continue repair after failures. Mark DONE only when the required checks actually pass, then stop dispatching that task. Preserve source revisions, model/backend identities, execution evidence and verified output fingerprints with the result.

Diagnose missing tools, skills, dependencies and services. Prepare task-relevant components from pinned inputs, verify their actual versions and resume the saved work.

Run the package tests and CLI integration checks when changing executable behavior. Documentation edits should keep examples aligned with the actual parser. Keep runtime snapshots, credentials, full conversations and user project data outside the public source tree.
