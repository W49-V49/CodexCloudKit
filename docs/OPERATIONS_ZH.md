# 更新、诊断、恢复与清理

## 更新共享核心

固定将要使用的发行提交，在云端源码目录重新安装包并运行 `setup`。复用未变化内容，核对发生变化的受管文件；项目自有规则和依赖保留。更新后在目标项目运行 `doctor` 与实际需要的调用测试。

当前 Codex Cloud 中，完成环境准备后保存并 Republish，再从新环境开始任务。旧任务保留自己的状态，后台刷新不会替代显式安装。

## 常见诊断

| 现象 | 检查顺序 |
| --- | --- |
| `cloudkit` 不在 PATH | 使用安装虚拟环境中的绝对路径，确认包安装位置 |
| attach 后规则没有自动生效 | 读取项目原规则和 `AGENTS.cloudkit.md`，查看接入结果和冲突项 |
| 新项目读取到旧项目状态 | 核对 project-root、project-id、分支和进程 cwd，按新身份重启 |
| 记忆无法启动 | 核对协议路径、原生依赖、模型版本、目录和真实返回码 |
| index 一直全量变化 | 核对项目根、内容清单、配置指纹和是否切换了分支 |
| worker 退出成功但项目仍有错误 | 查看独立验收命令结果，将失败证据反馈到修复轮次 |
| CLI 初始化只读错误 | 保存真实初始化结果，使用实际可用的执行路线，分别核验模型与命令能力 |
| 任务重启后重复执行 | 检查状态目录是否持久、租约是否恢复、输出指纹是否匹配 |
| 环境联网或认证失败 | 区分直接变量与代理网络密钥，核对域名、平台代理和凭据交付 |

## 失败路线与熔断

保存错误类型、日志、源版本和输出变化。同类错误两次或连续三次无进展后，停止该路线并选择适用的独立备用。备用路线成功后重新运行独立验收，而不是沿用上一条路线的成功标记。

如果后端暂不可用，将具体原因与下一条可恢复动作写入持久断点。命令调度状态、真实模型调用和业务验收分别记录。

## 巡检与续派工作流

将 [examples/autonomy.yml](../examples/autonomy.yml) 复制并提交到私有控制仓库默认分支的 `.github/workflows/autonomy.yml`。配置 `CLOUDKIT_SOURCE_REPOSITORY` 与 `CLOUDKIT_SOURCE_REF`，使用标签为 `[self-hosted, linux, x64, cloudkit]` 的云端 Runner。完整部署步骤见[自建 Runner](SELF_HOSTED_RUNNER_ZH.md)。

首次运行前，用该 Runner 的官方 Codex 登录执行真实模型 probe，再检查独立验收命令。之后模板通过即时 `workflow_dispatch` 推进下一轮，支持独立的 `repository_dispatch` 路线，并在每小时第 17 分钟巡检。

| 现象 | 检查位置 |
| --- | --- |
| 任务一直排队 | Runner 在线状态及 linux/x64/cloudkit 标签是否匹配 |
| checkout 工具箱失败 | 两项 source variables、固定 ref 和仓库读取权限 |
| 下一轮没有开始 | 持久 outbox、dispatch 返回结果、工作流是否位于默认分支 |
| 小时巡检没有运行 | 默认分支中的 cron、Actions 是否启用及实际队列记录 |
| 模型探测失败 | Runner 运行账号、真实官方登录、probe stdout/stderr 与后端版本 |
| 验收失败仍继续 | 下一轮是否携带失败证据，所选独立路线及熔断计数 |
| 任务完成后又被派发 | 任务 DONE 状态、事件去重键、过期 outbox 与租约 |

每轮产物 `cloudkit-round-<run id>` 含对应 JSON 结果，模板设置 artifact 保留 14 天。长期证据与恢复快照继续保存到私有控制存储，不能只依赖临时 artifact。更新工具箱版本时先验收新提交，再修改 `CLOUDKIT_SOURCE_REF` 并用一轮真实任务复验。

模板文件存在、CI 通过和真实模型持续运行分别记录。仅按源代码提供的模板，不把尚未部署到目标 Runner 的配置写成正在运行。

## 可选队列诊断

运行 `cloudkit queue ... inspect --task-id ...` 同时查看 Git 任务和 Redis 可用性。Redis 断开时先查看持久 outbox、运输错误次数与既有 GitHub 备用结果；重启 worker 后从 Git 租约与已处理事件恢复。队列 job 完成或队列清空不等于业务通过，仍以独立验收与 `DONE` 为准。完整操作见[RQ 队列](QUEUE_ZH.md)。

## 升级与回滚

更新前导出已验证的记忆和状态快照，记录包版本、模型指纹和源提交。升级后先运行增量/恢复验收，再切换活动版本。失败时恢复上一已验证版本；旧索引和新模型不混用。

## 清理顺序

先列出候选文件和保留依据，确认它们不被当前任务使用。对仍需留证的产物先归档、校验摘要并实际恢复验证，再清除工作副本。保留固定锁、实际验收日志、活动断点、有效记忆和当前需要的模型。源码、共享依赖、正式记忆、派生索引和临时日志按各自位置维护。
